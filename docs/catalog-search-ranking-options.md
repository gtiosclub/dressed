# Measure catalog relevance before choosing search infrastructure

**Recommendation:** For [Dressed issue #178](https://github.com/gtiosclub/dressed/issues/178), build a reproducible comparison of the existing SQLite search and one transparent, source-backed lexical/attribute ranker. Use a frozen 30–50-product fixture and independently judged queries, then decide whether SQLite FTS5 improves retrieval enough to adopt. This is a proposal and evaluation task, not a production search launch. Dedicated engines and paid services become useful when judged relevance, typo handling, catalog size, or operational requirements justify them. Photo similarity deserves a separate experiment on approved product images; no similarity score establishes that a photographed garment is the exact retailer product. The choice of retailer, image rights, refresh age, expected traffic, and hosting target remains open. Related project context: [[catalog-and-recognition-spec]], [[product-scope]], and [[architecture]].

## The existing prototype is a measurable baseline

The local catalog ingests reviewed JSON snapshots into SQLite, derives stable IDs from `(sourceId, externalId)`, and serves a read-only `/products` endpoint on loopback. Its demo feed contains **three synthetic products with `.example` URLs**; it is neither a live retailer catalog nor a source of working purchase links. Search filters `status='active'`, optionally filters category, matches the **whole query as a case-insensitive substring** of title or brand, and sorts by title then ID. It returns `total` and `nextOffset` with `limit` 1–100. Thus a multiword query such as `blue denim jacket` needs that contiguous phrase in a title or brand; the code does not compute a relevance score. The iOS client currently requests up to 100 results in one call, so its pagination behavior is not exercised. ([Catalog implementation](https://github.com/gtiosclub/dressed/blob/main/backend/catalog/catalog.py), [catalog README](https://github.com/gtiosclub/dressed/blob/main/backend/catalog/README.md), [iOS client](https://github.com/gtiosclub/dressed/blob/main/dressed/Discovery/ViewModels/CatalogService.swift))

An active record means it appeared in the latest complete scan, **not necessarily that it was checked recently**. One complete scan missing a product marks it `stale`, two mark it `unavailable`, and a partial scan does not age it out. Current URL validation checks HTTPS syntax and an allowed hostname supplied by the feed; it does not check live reachability, redirects, or that a destination still represents that item. Before live use, source configuration must be controlled by the backend rather than trusted from the feed. ([Catalog implementation](https://github.com/gtiosclub/dressed/blob/main/backend/catalog/catalog.py), [catalog README](https://github.com/gtiosclub/dressed/blob/main/backend/catalog/README.md))

## Search choices trade simple control for relevance features

The table separates **in-house ranking logic** from **open-source search engines** and **managed services**. “Photo” describes whether the option can retrieve image vectors or directly search an indexed product-image set; it does not imply garment detection, exact identity, or licensed access to retailer images. Pricing models are more useful here than point prices, which change and cannot be turned into a Dressed bill without traffic and deployment assumptions.

| Approach | Pros | Cons and operating cost | Photo similarity fit |
| --- | --- | --- | --- |
| **Current SQLite substring baseline; in-house** | Already implemented; zero new infrastructure; deterministic baseline. | Entire phrase must occur in title/brand; alphabetical rather than relevance order; no typo/synonym handling. | None without a separate pipeline. |
| **Token/attribute scorer; in-house** | Explainable scores and match reasons; cheap on a bounded catalog; easy to compare with current behavior. | Team owns normalization, synonyms, weights, tie-breaking, testing, and performance as the corpus grows. | Can be combined with a later vector score. |
| **SQLite FTS5; open source, embedded** | Tokenized search, prefix support, weighted columns and BM25 inside the existing database. ([SQLite FTS5](https://www.sqlite.org/fts5.html)) | External-content indexes need transactional synchronization and an initial rebuild; FTS query syntax must be safely constructed; typo tolerance and fashion synonyms need extra work. | Store vectors separately and brute-force a small set; FTS5 itself is text search. |
| **PostgreSQL full-text + pgvector; open source, self-hosted or managed Postgres** | Weighted `tsvector`, GIN indexing, lexical/vector retrieval in one database; pgvector supports exact search and HNSW/IVFFlat when scale warrants it. ([PostgreSQL text search](https://www.postgresql.org/docs/current/textsearch-controls.html), [indexes](https://www.postgresql.org/docs/current/textsearch-indexes.html), [pgvector](https://github.com/pgvector/pgvector)) | Migrating a working SQLite prototype just for search adds a database service; approximate vector indexes trade recall for speed and filtered search needs care. | Good if Postgres becomes the canonical catalog store. |
| **Meilisearch Community Edition; open source/self-hosted** | Typo tolerance, filters, configurable ranking and hybrid search; MIT-licensed self-hosted engine. ([Open source](https://www.meilisearch.com/open-source), [ranking and typo behavior](https://www.meilisearch.com/blog/typo-tolerance), [hybrid](https://www.meilisearch.com/products/hybrid-search)) | Separate index, synchronization, monitoring, backups, and hosting; embedding generation still needs a model/provider. | Accepts externally generated vectors for hybrid experiments. |
| **Typesense; open source/self-hosted** | Fast lexical/faceted search, typo tolerance, filters, vector and hybrid queries. ([Search API](https://typesense.org/docs/28.0/api/search.html), [vector search](https://typesense.org/docs/latest/api/vector-search.html)) | Separate service and index projection; review GPL-3.0 obligations for the intended deployment/distribution. ([Repository license](https://github.com/typesense/typesense)) | Vector candidate search with model-generated image embeddings. |
| **OpenSearch; open source/self-hosted** | Broad full-text, vector, filter, hybrid rank-fusion and snapshot/pagination controls. ([Hybrid search](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/index/), [PIT](https://docs.opensearch.org/latest/search-plugins/searching-data/point-in-time/)) | Most tuning and operational surface for a tiny pilot; image embedding remains separate. | Strong larger-catalog hybrid option. |
| **Algolia; managed** | Quick managed keyword search, rules, synonyms, suggestions and ranking controls. ([Pricing/features](https://www.algolia.com/pricing)) | Requests and records affect billing; typeahead can multiply requests. Standard keyword search is not an image recognition system. ([Image-search use case](https://www.algolia.com/use-cases/image-search)) | Convert recognized attributes into queries or arrange a separate visual pipeline. |
| **Typesense Cloud / Meilisearch Cloud; managed** | Hosted versions of engines above; less server maintenance while retaining familiar text/hybrid APIs. ([Typesense pricing](https://cloud.typesense.org/pricing/calculator), [Meilisearch pricing](https://www.meilisearch.com/pricing)) | Typesense has a provisioned-cluster idle floor; Meilisearch plans have usage/resource billing. Both still need canonical catalog synchronization and source checks. | Bring an embedding pipeline and approved product images. |
| **Elastic Cloud / AWS OpenSearch Service; managed** | Mature text/vector/hybrid features and managed operations. ([Elastic pricing](https://www.elastic.co/pricing), [AWS pricing](https://aws.amazon.com/opensearch-service/pricing/)) | Multiple resource, storage, or compute billing dimensions; comparatively heavy for the proposed fixture. | Vector index, with external image encoding. ([AWS vector guide](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/vector-search.html)) |
| **Google AI Commerce Search; managed commerce platform** | Product hierarchy, retail search, filters, and optimization around catalog/user events. ([Features](https://docs.cloud.google.com/gemini-enterprise-cx/ai-commerce-search/features), [pricing](https://cloud.google.com/products/retail/pricing)) | Better fit for a retailer with event data than a small multi-retailer prototype; integration and product-feed requirements are substantial. | Do not assume its text/catalog API equals a photo-product query. |
| **Google Vision API Product Search; managed photo lookup** | Direct apparel product-set and reference-image search, returning visual/semantic similarities. ([Overview](https://docs.cloud.google.com/vision/product-search/docs?hl=en), [pricing](https://cloud.google.com/vision/product-search/pricing)) | Needs an indexed, permitted product-image set and uploads query images; prediction and storage usage are metered. Scores are comparable **within** a query, not calibrated across queries. ([General tips](https://docs.cloud.google.com/vision/product-search/docs/general-tips)) | Most direct managed image-to-catalog experiment, not a text search replacement. |
| **Pinecone / Weaviate Cloud; managed vector stores** | Vector retrieval and metadata filters; Weaviate supports image queries with a suitable multimodal vectorizer. ([Pinecone pricing](https://www.pinecone.io/pricing/), [Weaviate image search](https://docs.weaviate.io/weaviate/search/near-media), [Weaviate pricing](https://weaviate.io/pricing)) | Index/storage/request or vector-dimension billing; Dressed must still handle crops, embeddings, retailer ingestion, freshness, identity, and links. | Useful only after embeddings prove value at a scale needing a service. |

For the current size, a hand-scored lexical candidate or FTS5 is the most proportionate **experiment**, not a predetermined production winner. Meilisearch or Typesense is the next comparison if the labeled set exposes typo/facet failures worth operational complexity. Algolia is the managed text-search comparison if the team values a fast hosted trial. OpenSearch, Elastic and commerce-specific platforms should enter a proof of concept only when a concrete requirement exceeds simpler choices. No Dressed-specific quality, p95 latency, or total-cost measurements exist yet.

## Build a frozen evaluation before integrating another engine

Create `backend/catalog/evaluation/products.json` with **30–50 synthetic or approved-source products** spanning tops, pants, dresses, shoes and outerwear. Keep fixed IDs, near-duplicates and variants, source-backed color/material/brand fields, at least one `stale`, one `unavailable`, and one `outOfStock` offer. Put deliberately invalid or missing URLs in a separate negative fixture because the normal importer rejects unapproved URLs. The size is a proposed pilot, not a scale target. Keep `queries.json` with **8–12 stable queries**: exact title, `blue denim jacket`, synonym (`jeans`/`denim pants`), brand plus type, broad category, misspelling, mixed attributes, category conflict and a no-result case. Write `qrels.json` independently of the rankers, grading every plausible candidate 0–3 with a short rationale (3 ideal, 2 useful substitute, 1 weak relation, 0 irrelevant). A different-brand blue denim jacket can be relevant but remains a substitute, never the identity of a photographed product. ([Issue #178](https://github.com/gtiosclub/dressed/issues/178))

Run **A: the current code unchanged** and **B: a token/attribute scorer** against the same frozen snapshot. B should normalize query tokens, apply a small reviewed synonym map, retrieve candidates through a simple scan or FTS5, then score title-token coverage, category agreement, and only source-backed color/material/brand; an exact phrase can earn a bonus. Freeze weights before using held-out queries and break all ties by stable product ID. FTS5 provides weighted `bm25()` if token retrieval becomes useful, but user strings must be escaped/constructed as literals rather than interpolated as query operators. Its external-content index needs insert/update/delete maintenance and a rebuild for existing rows. ([SQLite FTS5](https://www.sqlite.org/fts5.html))

Report **top-five IDs and explanations per query**, P@5 with relevance grade ≥2, NDCG@5, zero-result rate, and macro averages, while showing individual failures because a dozen queries give unstable averages. NDCG rewards highly relevant products near the top. ([scikit-learn NDCG reference](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.ndcg_score.html)) Add stale/unavailable leakage (target zero), out-of-stock policy observations, URL checks, cold/warm p50/p95 server-side latency, index-build time, corpus size, machine/runtime details, evaluation timestamp, and hashes of the input files. Check redirects and final hosts only on approved live sources; synthetic `.example` URLs must never count as verified retailer links. Tiny-fixture timings show comparative overhead, not production capacity.

An implementable runner can create two identical temporary SQLite databases from the fixture, invoke the existing `CatalogDatabase.search` for A, invoke B through a separate function, collect ordered IDs and timings, and write a machine-readable result plus a short Markdown comparison. Keep `rankingMode` internal to evaluation until B wins on held-out queries and the issue's proposal is reviewed. The result should state failure cases and the effect of each extra feature, not just a single aggregate score. The existing [recognition adapter](https://github.com/gtiosclub/dressed/blob/main/backend/recognition/README.md) supports live Object Localization for development, while Product Search remains fixture-only; it has not established real-photo retrieval quality and does not make this catalog evaluation an image-detection task.

## Keep ranking, identity and freshness as separate contracts

**Canonical catalog data stays authoritative.** If a dedicated engine is adopted, project only approved public fields keyed by stable product ID, upsert/delete after committed catalog changes, and periodically reconcile IDs, statuses and content hashes. Every public response should still join or validate against the canonical record. The backend enforces active/fresh/availability policy and returns a bounded DTO; never put an engine admin key in the iOS app. Define a source-specific maximum `lastCheckedAt` age and an explicit out-of-stock policy before production. The current `active` filter alone cannot enforce age freshness. Live product links need an approved source, HTTPS/final-host validation and periodic item-level checks; the existing allowlist check is only an initial validation. ([Catalog spec](https://github.com/gtiosclub/dressed/blob/main/docs/catalog-and-recognition-spec.md), [catalog implementation](https://github.com/gtiosclub/dressed/blob/main/backend/catalog/catalog.py))

The public response can preserve today's `products`, `total` and `nextOffset` while adding an explicit explanation and link state. A proposed result, with **illustrative fields rather than an implemented API**, is:

```json
{
  "id": "stable-catalog-id",
  "source": {"id": "approved-retailer", "name": "Example Retailer"},
  "title": "Blue denim jacket",
  "lastCheckedAt": "2026-10-15T00:00:00Z",
  "match": {"kind": "text", "label": "similar", "explanation": "Matches blue, denim, and outerwear"},
  "verifiedProductURL": null
}
```

`verifiedProductURL` remains null for unchecked or synthetic links. A verified URL attached to a **similar candidate** can support “Shop this similar item”; it does not prove that the user's photo shows that exact item. Reserve **“exact product” for independently established retailer identity** such as a checked retailer product ID/SKU/GTIN or a source URL demonstrably tied to the photographed item. An embedding score, same color, or high text rank proves no such identity. Until that evidence exists, use “Catalog results” for text search and “Similar items” for photo suggestions. ([Product scope](https://github.com/gtiosclub/dressed/blob/main/docs/product-scope.md), [catalog spec](https://github.com/gtiosclub/dressed/blob/main/docs/catalog-and-recognition-spec.md))

For the frozen evaluation, current `offset` pagination and a score-then-ID order are adequate. A mutable production index needs a cursor or snapshot version to avoid duplicate or skipped results between pages; OpenSearch, for example, documents point-in-time plus `search_after`. The iOS client also needs a separate paging implementation before production. ([OpenSearch PIT](https://docs.opensearch.org/latest/search-plugins/searching-data/point-in-time/), [search-after hybrid pagination](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/search-after/))

## Add photo ranking only when it answers a measured gap

If text/attribute ranking leaves a meaningful photo-query gap, create a **separate held-out image evaluation** with consented garment crops and product photos that Dressed may process. Compare a category/text baseline with image vectors from a versioned CLIP or SigLIP checkpoint, first scoring every permitted image directly for a small corpus. CLIP supplies paired image/text encoders; Google's SigLIP project and checkpoint provide another candidate. Check the exact chosen checkpoint terms and the retailer's image rights. ([CLIP repository](https://github.com/openai/CLIP), [Google big_vision](https://github.com/google-research/big_vision), [SigLIP checkpoint](https://huggingface.co/google/siglip-base-patch16-224/tree/main))

The pipeline is `reviewed crop → category gate → versioned image embedding → active/fresh catalog candidates → lexical/visual rerank → source and URL validation → similar-item response`. Store model version and image hash, re-embed changed images, purge removed products, and measure visual recall@5, category errors, latency and stale/link leakage separately from identity precision. pgvector or a vector service is warranted only if exact scoring misses a measured latency or scale target. A managed Google Vision Product Search trial can be compared on the **same** approved set, but its within-query scores should not be used as a universal exact-match threshold. Any hosted query-image transfer needs a documented privacy and retention decision; the local Object Localization bridge uses development images only and does not authorize real user-photo uploads. ([pgvector](https://github.com/pgvector/pgvector), [Vision Product Search tips](https://docs.cloud.google.com/vision/product-search/docs/general-tips), [recognition experiment](https://github.com/gtiosclub/dressed/blob/main/backend/recognition/README.md))

## Conclusion

Issue #178 can deliver a defensible recommendation without selecting a vendor prematurely: a frozen corpus, judged queries, baseline-versus-ranker results, and a source/freshness contract. If the richer lexical ranker does not improve useful top results, its added complexity is unjustified; if it does, SQLite or FTS5 preserves a simple path into the first catalog slice. A later engine or embedding decision should follow measured relevance and operating needs, with retailer access, image rights, and photo privacy settled before any live rollout.
